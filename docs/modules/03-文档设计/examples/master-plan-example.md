# 项目重放总纲：mini-flask

## 一、项目简介

- **原项目来源与定位**：`pallets/flask (simplified)` — 一个基于 WSGI 协议的轻量级 Python Web 框架，聚焦 Web 请求处理与路由分发的核心骨架。
- **核心功能概述**：提供声明式装饰器路由注册、`Request` / `Response` 请求响应封装、请求生命周期前后拦截中间件、统一异常处理以及模块化蓝图路由组织能力。
- **技术栈与运行环境**：Python 3.10+、标准库 `wsgiref` / `urllib.parse` / `http`，零第三方重框架依赖，使用 `pytest` 运行自动化测试。
- **重放最终目标**：在 `replay/` 中从零构建一个支持动态路由、请求上下文解析、中间件拦截、统一异常处理及蓝图模块化挂载的可用微型 Web 框架。

## 二、原参考项目总架构拆解

### 2.1 整体架构

```text
+-------------------------------------------------------+
|                   WSGI Server (wsgiref)               |
+---------------------------+---------------------------+
                            | environ, start_response
                            v
+-------------------------------------------------------+
|                  App (WSGI Application)               |
|  +-----------------+       +-----------------------+  |
|  |  Blueprint 注册  | ----> |  Router (URL 匹配表)  |  |
|  +-----------------+       +-----------+-----------+  |
|                                        |              |
|  +-----------------+       +-----------v-----------+  |
|  |  Middleware 链  | <---> |  Context (Request栈)  |  |
|  +-----------------+       +-----------+-----------+  |
|                                        |              |
|  +-----------------+       +-----------v-----------+  |
|  |  Error Handler  | <---- |  View Function 视图   |  |
|  +-----------------+       +-----------+-----------+  |
|                                        |              |
|                            +-----------v-----------+  |
|                            |  Response 封装输出     |  |
|                            +-----------------------+  |
+-------------------------------------------------------+
```

- **接入层（App）**：实现 WSGI 可调用入口 `__call__(environ, start_response)`，统一驱动单次请求生命周期。
- **路由与组织层（Router / Blueprint）**：维护 URL 规则与 HTTP 方法到视图函数的映射，支持按业务模块聚合前缀路由。
- **执行与上下文层（Context / Middleware / View）**：将原始 `environ` 封装为 `Request` 并管理请求上下文栈，在视图执行前后串联中间件钩子。
- **输出与兜底层（Response / Error Handler）**：将视图返回值标准化为 HTTP 响应字节流，并在异常抛出时转交注册的错误处理器兜底返回。

### 2.2 数据流图

```text
HTTP 客户端请求
   │
   ▼
[1. WSGI Server] ──► 构造 environ 字典 & start_response 回调
   │
   ▼
[2. App.__call__] ──► 封装 Request 对象，压入当前请求上下文
   │
   ▼
[3. Before Middleware] ──► 按序执行前置钩子（若提前返回非空响应则短路跳过视图）
   │
   ▼
[4. Router.match] ──► 按路径与 HTTP Method 匹配视图函数并提取路径参数
   │                    ├── 未匹配 / 方法不支持 ──► 触发 404 / 405 异常
   │                    └── 匹配成功
   ▼
[5. View Function] ──► 执行业务逻辑，返回字符串 / 字典 / 元组 / Response
   │                    └── 抛出异常 ──► 交由 [Error Handler] 转换为错误响应
   ▼
[6. Response 封装 & After Middleware] ──► 统一封装状态码与响应头，执行后置钩子
   │
   ▼
[7. 上下文清理 & WSGI 输出] ──► 弹出请求上下文，调用 start_response 输出响应字节流
```

1. WSGI 服务器接收客户端 HTTP 请求，传入原始 `environ` 字典与 `start_response` 回调。
2. `App` 将 `environ` 封装为 `Request` 对象并压入当前请求上下文，随后按注册顺序执行前置中间件。
3. `Router` 根据请求路径和 HTTP 方法定位目标视图并提取动态路径参数；若无匹配或方法不允许则抛出 404/405 交由错误处理流程。
4. 视图函数执行并返回业务结果，经 `Response` 标准化与后置中间件加工后，清理上下文并向客户端输出完整 HTTP 响应。

### 2.3 核心数据设计

| 核心对象 / 数据结构 | 关键属性与类型 | 核心职责说明 |
| :--- | :--- | :--- |
| `Request` | `method: str`, `path: str`, `args: dict[str, str]`, `headers: dict[str, str]`, `body: bytes`, `json: Any \| None` | 封装 WSGI `environ` 中的 HTTP 请求信息，供路由匹配与视图函数读取 |
| `Response` | `body: bytes`, `status_code: int`, `headers: dict[str, str]`, `content_type: str` | 统一封装视图返回值与错误输出，供后置中间件加工并序列化为 WSGI 字节流 |
| `RouteRule` | `pattern: str`, `methods: set[str]`, `view_func: Callable`, `param_names: list[str]` | 表示单条已注册的 URL 路由规则，支撑静态/动态路径匹配与 HTTP 方法校验 |
| `RequestContext` | `app: App`, `request: Request` | 绑定单次请求作用域的上下文载体，通过请求上下文栈实现压栈激活与结束自动清理 |

## 三、分阶段重放路线详解

> 总计 `4` 个阶段，以下阶段编号与标题与 `workbench/state.json` 中的 `stages[]` 保持 1:1 一致。

### Stage 01：最小 HTTP 路由与响应骨架

- **演进目标（新增功能）**：从零搭建基于 WSGI 协议的最小可运行 Web 应用，新增 `App` 核心入口类、静态路径路由装饰器（`@app.route("/path")`）、基础纯文本 HTTP 200 响应输出以及本地开发服务器启动方法。
- **范围边界**：
  - **本阶段包含**：
    - `App` 类实现 WSGI `__call__` 接口与 `run()` 本地启动方法；
    - 静态路径（如 `/`、`/hello`）的路由注册与精确匹配；
    - 默认支持 `GET` 方法，返回 `text/plain` 文本响应；
    - 访问未注册路径时返回默认 `404 Not Found` 文本响应。
  - **本阶段暂不实现**：
    - 动态路径参数（如 `/users/<id>`）、Query 参数与请求体解析（留待 Stage 02）；
    - `Request` 对象与请求上下文栈（留待 Stage 02）；
    - 前置/后置中间件与自定义错误处理器（留待 Stage 03）；
    - 蓝图分组与 JSON/重定向响应快捷封装（留待 Stage 04）。
- **验收标准（怎么算通过）**：
  1. 启动本地服务后，请求已注册的静态路由能返回 HTTP `200 OK` 及预期文本正文。
  2. 请求未注册路径时返回 HTTP `404 Not Found`，且服务进程保持正常运行不崩溃。
  3. 覆盖「正常路由命中」与「404 未命中」的自动化测试全部通过。

### Stage 02：请求上下文与参数解析

- **演进目标（新增功能）**：在 Stage 01 骨架上，新增 `Request` 对象封装、动态 URL 路径参数提取（如 `/users/<id>`）、多 HTTP 方法校验（`GET` / `POST` 等）、Query 与 JSON 请求体解析，以及隔离请求的上下文栈机制。
- **范围边界**：
  - **本阶段包含**：
    - `Request` 类封装 `method`、`path`、`args`（Query 参数）、`headers`、`body` 与 `json` 解析；
    - 路由规则支持 `methods=[...]` 校验，方法不允许时返回 `405 Method Not Allowed`；
    - 路由支持基础动态路径参数提取并作为关键字参数注入视图函数；
    - 实现请求生命周期内的上下文压栈与自动出栈清理。
  - **本阶段暂不实现**：
    - 请求前后中间件拦截链（留待 Stage 03）；
    - 自定义异常处理器注册（留待 Stage 03）；
    - 蓝图多文件模块化拆分与 `jsonify` / `redirect` 等高级响应封装（留待 Stage 04）。
- **验收标准（怎么算通过）**：
  1. 注册带动态参数的路由与 `POST` 路由后，能正确解析路径参数、Query 参数和 JSON 请求体并返回预期结果。
  2. 向仅允许 `GET` 的路由发送 `POST` 请求时，稳定返回 HTTP `405`。
  3. 连续或并发请求结束后请求上下文栈清空（无跨请求数据串扰），自动化测试全部通过。

### Stage 03：中间件与错误处理管线

- **演进目标（新增功能）**：新增请求前后拦截钩子（`before_request` / `after_request`）与统一错误处理注册机制（`@app.errorhandler(...)`），支持前置钩子短路拦截与业务/HTTP 异常的自定义响应转换。
- **范围边界**：
  - **本阶段包含**：
    - 按注册顺序执行多个 `before_request` 钩子，任意钩子返回非空响应时短路跳过后续钩子与视图；
    - 按顺序执行 `after_request` 钩子，支持统一修改响应头（如注入耗时或跨域头）；
    - 捕获路由匹配及视图执行中的 HTTP 异常（404 / 405）与自定义异常，交由已注册处理器渲染，未捕获异常兜底返回 `500`；
    - 异常路径下通过 `try ... finally` 确保请求上下文栈正常出栈。
  - **本阶段暂不实现**：
    - 蓝图级路由前缀聚合与多文件模块化挂载（留待 Stage 04）；
    - `Response` 高级快捷构造函数（如 `jsonify`、`redirect`，留待 Stage 04）。
- **验收标准（怎么算通过）**：
  1. 多个前置/后置钩子按预期顺序执行；当前置钩子触发短路返回时，目标视图函数不被调用。
  2. 自定义 `404` 与业务异常处理器均能生效，未捕获异常返回 `500` 而不中断服务进程。
  3. 异常发生后继续发起正常请求，上下文隔离完好无污染，测试套件全部通过。

### Stage 04：蓝图模块化与响应封装

- **演进目标（新增功能）**：新增 `Blueprint` 蓝图模块化路由组件与完整的 `Response` 响应封装（支持自定义状态码、响应头、`jsonify` 及 `redirect`），支持按业务模块拆分文件并带 `url_prefix` 注册至主 `App`。
- **范围边界**：
  - **本阶段包含**：
    - 完善 `Response` 类，支持自定义状态码、响应头字典、`Content-Type` 与字节流序列化；
    - 新增 `jsonify()` 与 `redirect()` 快捷响应函数，支持视图直接返回 `dict` 或 `(body, status_code)` 元组自动转换；
    - 新增 `Blueprint` 类，支持独立声明路由并配置 `url_prefix`，通过 `app.register_blueprint(bp)` 合并至主路由表；
    - 以多模块蓝图结构组织示例应用完成端到端验证。
  - **本阶段暂不实现**：
    - Jinja2 模板渲染引擎、静态文件托管与 Session 加密签名（超出本次重放 MVP 范围）。
- **验收标准（怎么算通过）**：
  1. 创建至少 2 个不同 `url_prefix` 的蓝图并注册至 `App`，各前缀路由均能正确匹配并响应。
  2. 视图返回 `dict`、`(body, status)` 元组或 `Response` 对象时，均输出正确的状态码与 `Content-Type`。
  3. 覆盖 Stage 01–04 的全量回归测试一键运行全部通过。
