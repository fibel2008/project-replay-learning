## 一、模块目标与范围边界

### 1.1 核心定位

`workbench/project-records/master-plan.md`
是**每次阶段推进对话冷启动时的项目全局参考资料**（同时作为总对话在阶段 A 拆解 PRD、阶段 C
对照验收的全局基准），用于让新开的阶段对话在低上下文噪音下快速建立：

- 项目整体背景、技术栈与最终重放目标；
- 原参考项目的整体架构、核心数据流与核心数据设计；
- 分阶段重放演进路线、每阶段具体新增的功能边界与通过标准。

### 1.2 本模块范围（In Scope）

- 定义 `master-plan.md` 的三段式章节结构与各区块字段填写标准（“适中颗粒度”控制）。
- 明确总纲的读写权限规则及与 `workbench/state.json` 的 1:1 一致性约束。
- 产出可直接照搬填充的标准空白 Markdown 模板，以及 1 份独立示例文件（[master-plan-example.md](examples/master-plan-example.md)）。

### 1.3 本模块不管（Out of Scope）

- ❌ 大项目源码如何逆向拆解、切块与控制单次读取范围的具体方法论（属于 `#04` `02-03 大项目源码拆解与范围控制`；本单仅定义最终呈现结构）。
- ❌ 阶段 X 的详细 PRD 与学习记录正文模板（属于 `#05` `03-02`）。
- ❌ 阶段推进对话的身份提示与行为规则（统一归入 Skill `05-01` / `05-02`，不写入总纲）。
- ❌ `personal/` 迁移项目相关内容（MVP 阶段已裁剪，不设占位）。
- ❌ 所需知识框架与能力地图、路径修订记录表、单阶段知识点清单与对应原项目源码范围（本单已拍板裁剪，保持总纲精炼）。

## 二、核心设计规则与权限约束

1. **物理路径**：固定为 `workbench/project-records/master-plan.md`（对齐 `04-01`）。
2. **读写权限（覆盖早期局部锁定旧共识）**：3. **总对话（Master）**：唯一拥有创建与修改权的角色，**可修改全文任意内容**；**不维护路径修订记录表**，文档始终作为当前最新全局规划快照。
4. **软约束**：总对话原则上不回改「已完成阶段（`status == "done"`）」的路线定义，避免总纲与历史 PRD / 学习记录失真；修改一般仅用于修正架构理解或调整尚未开始的后续阶段。
5. **阶段推进对话（Stage X）**：严格只读，**禁止修订**总纲任何内容。
6. **与 `stage-<NN>-map.md`、`state.json` 的三方 1:1 强一致约束**：
7. 总纲第三章的阶段总数、阶段编号（`Stage 01 .. Stage NN`）及阶段标题，必须与 `workbench/project-records/stage-maps/stage-<NN>-map.md`（共 `X` 份）及 `workbench/state.json` 中的 `project.total_stages` / `stages[].stage / title` 保持严格三方 1:1 一致；若总对话增删或调整阶段路线，必须同步更新 `master-plan.md`、对应的 `stage-<NN>-map.md` 与 `state.json`。
8. **内容颗粒度原则（适中限制）**：
9. **不过简**：每阶段必须写清「相较上一阶段具体新增了什么功能」「本阶段包含 vs 本阶段暂不实现」「怎么算通过」，为阶段对话划清硬边界，防止剧透后续阶段或越界发挥。
10. **不过繁**：不塞入目录树、逐文件源码范围清单、知识图谱/语法教程、详细接口字段级测试用例或身份 Prompt，避免与 `stage-<NN>-prd.md` 重复并控制冷启动上下文消耗。

## 三、`master-plan.md` 章节结构与字段规范

总纲固定采用 **三段式结构**，严禁随意增加冗余章节：


| 章节                                   | 必填子项                                                                                                                                                                                                                                                                                  | 编写标准（适中颗粒度）                                                                                                                                                                                                                                                                                   | 严禁塞入的内容                                                                                                          |
|:-----------------------------------------|:----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|:--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|:-------------------------------------------------------------------------------------------------------------------------------|
| **一、项目简介**                   | 1. 原项目来源与定位<br>2. 核心功能概述<br>3. 技术栈与运行环境<br>4. 重放最终目标<br>5. 重放范围说明                                                                                                                                                                | 简明扼要讲清原项目来源与定位、最核心的几项能力、技术栈版本、全部重放完成形态，以及经用户拍板的功能级裁剪子系统及理由（无裁剪则注明完整重放核心主干）                                                                                                                                                      | 阶段对话身份提示、Skill 指令、`personal/` 迁移题说明                                                          |
| **二、原参考项目总架构拆解** | 1. **整体架构**（ASCII / Mermaid 架构图 + 简明分层说明）<br>2. **数据流图**（端到端主调用流转图 + 关键步骤说明）<br>3. **核心数据设计**（核心对象/数据结构的关键属性与职责）                                          | 聚焦「整体架构」「数据流图」「核心数据设计」三块，让阶段对话一眼看清全局组件边界、主链路流转及关键实体数据结构（如 `Request` / `Response` 核心属性）                                                                                                  | 完整目录树、逐文件职责清单、大段源码或完整类实现代码、设计思想长篇论述、边角裁剪清单 |
| **三、分阶段重放路线详解**    | 按 `Stage 01 .. Stage NN` 顺序展开，每阶段固定 **4 个槽位**：<br>1. **阶段编号与标题**<br>2. **演进目标（新增功能）**<br>3. **范围边界（本阶段包含 / 本阶段暂不实现）**<br>4. **验收标准（怎么算通过）** | - 编号与标题严格对齐 `state.json`<br>- **演进目标**须具体点出本阶段新增了什么功能<br>- **范围边界**须同时写明“包含什么”与“暂不实现什么”，防止阶段对话剧透<br>- **验收标准**写 2–4 条可观察、可验证的通过条件 | 本阶段聚焦知识点清单、对应原项目文件/行号清单、详细字段级 PRD 规格、路径修订历史表       |

## 六、与上下游模块的接口衔接

- **回溯同步 `04-01`（学习目录结构与权限边界）**：本模块确认 `master-plan.md` 权限为「仅总对话可修改全文（软约束不回改已完成阶段）、不设路径修订记录表」，覆盖了 `04-01` 权限表中“禁止修改学习目标/项目范围、修订须留痕”的旧表述，待后续同步更新 `04-01` 并记入 `PROJECT_MANAGEMENT.md` 决策日志。
- **对接 `04-02`（状态文件与多对话交接协议）**：阶段 0 生成 `master-plan.md` 时，其第三章的阶段总数、编号与标题必须与 `workbench/project-records/stage-maps/stage-<NN>-map.md` 及 `workbench/state.json` 的 `project.total_stages` / `stages[]` 严格保持三方 1:1 对齐；后续总对话若增删或调整阶段路线，须同步刷新 `stage-maps/stage-<NN>-map.md` 与 `state.json`。
- **对接 `02-03`（大项目源码拆解与范围控制，`#04`）**：本模块定义了总纲的「三段式呈现格式（含第二章的整体架构 + 数据流图 + 核心数据设计，以及每阶段 4 槽位）」；`02-03` 负责通过两层裁剪、5 步逆向拆解填充本总纲并同步生成 `stage-maps/stage-<NN>-map.md`，三方保持 1:1 对齐。
- **对接 `03-02`（项目记录与学习记录，`#05`）与 `01-02`（阶段 A 发布需求）**：阶段 A 读取总纲对应阶段的「演进目标 + 范围边界 + 验收标准」，将其展开细化为当阶段的 `workbench/project-records/stage-<NN>-prd.md`。
- **对接 `05-01` / `05-02`（Skill 架构与双模式路由）**：阶段对话的身份提示与只读约束由 Skill 统一注入，总纲保持纯项目上下文。
